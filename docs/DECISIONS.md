# Журнал решений

Сюда записываются решения, которые влияют на будущие шаги: выбор технологий, форматы, структура состояния,
отступления от GDD. Формат записи: контекст → решение → последствия. Новые записи — в конец.
Отменённое решение не удаляется, а помечается «Заменено ADR-NNN».

## ADR-001. Веб-стек: TypeScript + Vite, игра работает в браузере

**Шаг:** 0.1

**Контекст.** Игру пишут сессии ИИ в облачном контейнере без экрана. Владелец оценивает результат по скриншотам
и живой сборке. Нужны: автоматические скриншоты, запуск симуляции без графики, простая публикация.

**Решение.** TypeScript, сборка Vite, игра — веб-страница. Тесты — Vitest, линтер — Biome.

**Последствия.**

- В контейнере уже есть Chromium и Playwright → скриншоты и дымовые проверки без настройки.
- Симуляция на TypeScript запускается в Node без графики тем же кодом, что и в браузере.
- Публикация — GitHub Pages: владелец открывает игру по ссылке с любого устройства.
- Позже игру можно упаковать в настольное приложение (Tauri/Electron) без переписывания.

## ADR-002. Отрисовка на Canvas 2D без игрового движка

**Шаг:** 0.1

**Контекст.** Игре нужны тайловая карта до 512×512, до ~1500 жителей, частицы, ночной свет, перекраска палитрой.

**Решение.** Собственный лёгкий рендерер на Canvas 2D: карта кешируется чанками 32×32 тайла во внекадровые холсты,
спрайты жителей собираются из слоёв один раз и кешируются, свет и время суток — наложением слоёв.

**Почему не движок (PixiJS, Phaser).** Меньше движущихся частей на полторы сотни сессий: нет смены версий API,
нет зависимости от WebGL в безэкранном браузере, отрисовка полностью предсказуема для скриншотов.
Нагрузка игры (десятки тысяч мелких `drawImage` за кадр) укладывается в возможности Canvas 2D.

**Последствия.** Отрисовка спрятана за собственным интерфейсом в `src/render`. Если замеры на шаге 10.11
покажут нехватку скорости, рендерер заменяется на WebGL отдельным шагом, не затрагивая симуляцию.

## ADR-003. Графика как код

**Шаг:** 0.1 (реализация — шаг 0.3)

**Контекст.** Графику создают те же сессии ИИ, что и код. Рисовать файлы-картинки они не могут, а редактировать
текст — могут; GDD требует перекраски палитрой (тон кожи, сезоны, эпохи) и конструктора жителя из слоёв.

**Решение.** Спрайт описывается текстом: сетка символов + легенда «символ → цвет мастер-палитры».
При запуске спрайты растеризуются в атлас. Просмотр — отладочная сцена-галерея и скриншот.

**Последствия.** В репозитории нет бинарных ресурсов; изменения графики видны в diff; перекраска — подмена палитры;
любой спрайт можно править точечно. Ограничение: это пиксель-арт малого разрешения, что и предусмотрено GDD.

## ADR-004. Базовый набор графики — на этапе 0, а не серые заглушки до этапа 5

**Шаг:** 0.1

**Контекст.** GDD (§14.1, принцип 1) предлагает делать первые этапы на серых заглушках. Но владелец оценивает
каждый шаг по скриншотам, и при графике-как-коде черновой, но стильный набор стоит дёшево.

**Решение.** На шагах 0.3–0.4 создаются палитра и базовый набор графики эпохи 0. Этапы 1–4 сразу выглядят как игра.
Принцип GDD сохраняется в главном: новые системы сначала получают простую графику, а доводка до финального
качества, полный набор анимаций и сезонов — этап 5.

**Последствия.** Скриншоты с первого этапа понятны неспециалисту. На этапе 5 графика дорабатывается, а не создаётся с нуля.

## ADR-005. Таблицы данных — JSON в `data/`

**Шаг:** 0.1 (реализация — шаг 0.5)

**Решение.** Содержание и баланс — в `data/*.json`; типы и проверка — в `src/data/`. JSON читается одинаково
в браузере и в Node и позже позволит пользовательские таблицы (GDD, «После выпуска»).

## ADR-007. Дорожная карта GDD переработана под сессии

**Шаг:** 0.1

**Контекст.** Раздел 14 GDD рассчитан на команду и месяцы; часть его шагов слишком велика для одной сессии,
часть требует людей (показ зрителям).

**Решение.** Рабочая дорожная карта — `docs/ROADMAP.md`: те же 13 этапов и тот же порядок, но шаги нарезаны так,
чтобы каждый помещался в одну сессию; крупные шаги GDD разделены; в конце каждого этапа добавлена ревизия;
показы зрителям заменены проверкой владельцем на живой сборке. Карточки этапов 0–5 подробные, этапов 6–12 — краткие
и уточняются ревизией предыдущего этапа.
