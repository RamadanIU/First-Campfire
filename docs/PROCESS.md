# Порядок работы над шагом

Этот документ — обязательный регламент каждой сессии. Одна сессия выполняет **один шаг** дорожной карты
от начала до конца: понять → сделать → проверить → записать → открыть PR → отчитаться.

Настройки процесса (их меняет только владелец проекта):

| Настройка      | Значение                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| Слияние PR     | **Вручную владельцем.** Сессия сама мержит PR только если владелец прямо попросил об этом в этой сессии |
| Основная ветка | `main`                                                                                                  |
| Живая сборка   | <https://ramadaniu.github.io/First-Campfire/> (обновляется после слияния в `main`)                      |

---

## 1. Начало сессии

1. **Зависимости и статус.** При старте облачной сессии автоматически выполняются `npm install` и `npm run next`.
   Если этого не произошло — выполни их вручную.
2. **Незакрытые PR.** Проверь открытые pull request'ы репозитория. Если PR предыдущего шага ещё не слит в `main`,
   то `main` не содержит его результата и начинать новый шаг нельзя. Сообщи об этом владельцу и предложи слить PR
   (самостоятельно — только с его прямого согласия и при зелёном CI). После слияния обнови `main` и продолжай.
3. **Исходное состояние.** Выполни `npm run check`. Если что-то красное ещё до твоих изменений — сначала почини,
   это часть работы; упомяни в отчёте.
4. **Определи шаг.** Шаг, названный владельцем, либо первый невыполненный из `npm run next`. Шаги идут по порядку:
   пропускать шаг можно только по прямому указанию владельца.
5. **Прочитай контекст** (и только его — весь GDD читать не нужно):
   - `docs/STATUS.md` — текущее состояние игры и подсказки;
   - карточку шага в `docs/roadmap/stage-NN.md` и вступление к этапу в том же файле;
   - отчёты 1–2 предыдущих шагов в `docs/journal/`;
   - разделы GDD из карточки (`docs/gdd/`), а при работе с числами — `docs/gdd/13-balance-numbers.md`;
   - `docs/ARCHITECTURE.md`; при необходимости `docs/DECISIONS.md`, `docs/ART.md`, `docs/BACKLOG.md`.
6. **Изучи код**, который будешь менять, прежде чем писать новый. Переиспользуй существующее.
7. **Составь план** на сессию (список задач) и коротко сообщи его владельцу простыми словами.

## 2. Работа

- Двигайся небольшими законченными изменениями; коммить по смыслу (`шаг 1.4: …`).
- Соблюдай правила из `docs/ARCHITECTURE.md` — особенно детерминизм симуляции, отделение симуляции от отрисовки,
  содержание в таблицах данных и видимую причину у каждого события.
- Числа баланса бери из GDD (раздел 13 и раздел системы). Числа живут в `data/`, а не в коде.
- Пиши тесты вместе с кодом. Каждый критерий готовности из карточки должен быть чем-то подтверждён:
  тестом, выводом команды или скриншотом.
- Не выходи за рамки шага. Попутные находки, идеи, отложенные мелочи записывай в `docs/BACKLOG.md`.
- Если принял решение, влияющее на будущие шаги (формат данных, структура состояния, отступление от GDD), —
  запиши его в `docs/DECISIONS.md`.

### Если шаг оказался слишком большим

Не сдавай полусделанное и не раздувай сессию. Раздели шаг:

1. Выдели законченную часть, после которой игра работает и которую можно показать.
2. В `docs/ROADMAP.md` и в карточке переименуй шаг в `N.Mа`-вариант латиницей: `4.5` → `4.5a`, и добавь следом
   `4.5b` с тем, что осталось (полноценная карточка: цель, что сделать, критерии).
3. Выполни и закрой `4.5a` по всем правилам. `4.5b` достанется следующей сессии.

### Если что-то мешает закончить

- Упавшие тесты, ошибки сборки, сбои инструментов — разбирайся и чини, это обычная работа.
- Нужна информация или решение, которое может принять только владелец (вкус, приоритеты, деньги, доступы), —
  спроси коротко и по существу, предложив вариант по умолчанию. Всё, что от ответа не зависит, доделай.
- Если критерий из карточки невыполним или противоречит уже сделанному — не подгоняй результат.
  Опиши проблему в отчёте, предложи исправление карточки и согласуй с владельцем.

## 3. Проверка — «определение готовности»

Шаг готов, только когда выполнено **всё**:

1. **Критерии карточки.** Каждый пункт «Готово, когда» выполнен и имеет подтверждение.
2. **`npm run check` зелёный** (линтер, типы, тесты, дорожная карта, сборка).
3. **Тесты.** Новая логика покрыта тестами; тест детерминизма проходит; ни один тест не удалён и не отключён.
4. **Глазами.** Сняты скриншоты (см. ниже), ты открыл каждый и убедился: картинка соответствует задуманному,
   нет артефактов, наложений, пустых мест, нечитаемого текста. Некрасиво или непонятно — значит, не готово.
5. **Прогоны без графики** (с шага 0.6): `npm run sim` на нескольких зёрнах проходит без ошибок;
   в отчёт внесены ключевые показатели. Смерть жителя при доступной еде и воде — это ошибка ИИ, а не «не повезло».
6. **Нет регрессий.** Контрольные сцены из `docs/STATUS.md` по-прежнему выглядят и работают правильно.
7. **Производительность.** Если шаг затрагивает тик симуляции или отрисовку — измерь и запиши в отчёт.

### Скриншоты

- Снимаются командой `npm run shot -- --step <id> имя="?параметры" …` и сохраняются в `docs/screenshots/<id>/`.
  Команда падает, если на странице есть ошибки, — это тоже проверка.
- Любое состояние игры должно воспроизводиться адресной строкой (`?scene=…&seed=…&ticks=…&cam=…&zoom=…`).
  Если нужный кадр нельзя получить параметрами — добавь параметр или отладочную сцену, это часть шага.
- Сколько: **2–5 кадров на шаг.** Обязательно: (1) новое, что появилось в шаге, крупно; (2) общий вид игры.
  Для систем «во времени» — кадры «до» и «после» (например, день 1 и день 30).
- Для шагов без видимых изменений — общий вид игры (доказательство, что всё работает) и вывод проверок в отчёте.
- Подписывай кадры в отчёте: что на них и на что смотреть.

## 4. Запись прогресса

Делается **до** создания PR, входит в тот же PR.

1. **Отчёт шага** — `docs/journal/<id>.md` по шаблону [`docs/journal/TEMPLATE.md`](journal/TEMPLATE.md).
2. **`docs/STATUS.md`** — перепиши так, чтобы новый человек понял, что игра умеет теперь, как это увидеть,
   что известно плохого и что важно знать следующему шагу. Это снимок состояния, а не история: устаревшее удаляй.
3. **`npm run roadmap -- done <id>`** — отметит шаг в `docs/ROADMAP.md` (не правь галочку вручную:
   команда заодно проверит, что отчёт и скриншоты на месте).
4. **Сопутствующие документы**, если затронуты: `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/ART.md`,
   `docs/BACKLOG.md`, карточки будущих шагов (если твоя работа меняет их условия — поправь их).
5. Финальный `npm run check`.

## 5. Pull request

1. Закоммить всё и отправь в ветку, назначенную сессии (если ветка не назначена — `step/<id>-кратко`).
2. Создай PR в `main` по шаблону `.github/pull_request_template.md`. Заголовок: `Шаг <id> — <название>`.
3. Вставь скриншоты в описание: `npm run roadmap -- shots <id>` выдаст готовую разметку
   (ссылки привязаны к коммиту, поэтому сначала push, потом генерация).
4. Дождись завершения CI. Красный — чини и отправляй исправление, пока не станет зелёным.
   Исключение — CI **не запустился** не по вине кода: задача завершается за 2–3 секунды, исполнитель не назначен,
   лог недоступен (например, аккаунт GitHub заблокирован из-за оплаты). Чинить тут нечего: убедись, что
   `npm run check` зелёный локально после чистой установки (`npm ci`), запиши ситуацию в отчёт и скажи владельцу,
   что именно нужно исправить на его стороне. Причину видно в аннотациях проверки:
   `https://api.github.com/repos/RamadanIU/First-Campfire/check-runs/<id проверки>/annotations`.
5. Слияние — по настройке в начале этого документа.

## 6. Итоговое сообщение владельцу

Последнее сообщение сессии — отчёт простым языком:

1. **Что сделано** — 2–5 предложений о том, что изменилось в игре с точки зрения зрителя.
2. **Скриншоты** — отправь файлы в чат (если доступен инструмент отправки файлов) и подпиши, на что смотреть.
3. **Как проверено** — коротко: какие проверки пройдены, ключевые цифры.
4. **Ссылка на PR** и состояние CI.
5. **Что не получилось или вызывает сомнения** — честно, если есть.
6. **Нужно ли что-то от владельца** — решения, оценка внешнего вида, слияние PR.
7. **Следующий шаг** — его номер и название.

Не пиши длинных технических описаний: подробности есть в отчёте шага и в PR.

## Ревизия этапа

Последний шаг каждого этапа — ревизия. Новых возможностей в ней нет; её задача — убедиться, что этап
действительно закончен, и подготовить следующий. Стандартное содержание:

1. **Перепроверка этапа.** Пройти критерии всех шагов этапа заново на текущей сборке; результаты — таблицей в отчёте.
   Сломанное — починить.
2. **Проверка этапа целиком** — условие, записанное во вступлении к этапу («Проверка этапа»).
3. **Прогоны.** Серия прогонов без графики на 20+ зёрнах; показатели сравнить с целями GDD (разделы 13 и 15.2),
   подстроить числа в `data/`.
4. **Техдолг.** Разобрать `docs/BACKLOG.md`: сделать то, что мешает следующему этапу, остальное оставить.
   Упростить код, который усложнился; убрать мёртвый.
5. **Документы.** Привести `docs/ARCHITECTURE.md` и `docs/STATUS.md` в соответствие с реальностью;
   обновить список контрольных сцен.
6. **План следующего этапа.** Перечитать карточки следующего этапа с учётом реального кода: уточнить,
   детализировать (до уровня этапов 0–1), разделить слишком большие шаги, добавить недостающие.
   Карточки поздних этапов написаны кратко именно в расчёте на это уточнение.
7. **Вопросы владельцу.** Список того, что стоит посмотреть в живой сборке и на что дать отзыв.
   Отзывы владельца записываются в `docs/FEEDBACK.md` и учитываются в следующих шагах.

## Где что лежит

| Файл                       | Назначение                                                                   | Кто меняет                                 |
| -------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------ |
| `CLAUDE.md`                | Краткие правила, загружаются в каждую сессию                                 | Редко, по согласованию с владельцем        |
| `docs/PROCESS.md`          | Этот регламент                                                               | Редко, по согласованию с владельцем        |
| `docs/ROADMAP.md`          | Список всех шагов с отметками — **единственный источник правды о прогрессе** | `npm run roadmap -- done`                  |
| `docs/roadmap/stage-NN.md` | Карточки шагов этапа                                                         | Ревизии этапов; сессии при разделении шага |
| `docs/STATUS.md`           | Снимок текущего состояния игры                                               | Каждая сессия                              |
| `docs/journal/<id>.md`     | Отчёт о шаге                                                                 | Сессия, выполнившая шаг                    |
| `docs/screenshots/<id>/`   | Скриншоты шага                                                               | `npm run shot`                             |
| `docs/ARCHITECTURE.md`     | Устройство кода и технические правила                                        | По мере изменений                          |
| `docs/DECISIONS.md`        | Журнал принятых решений                                                      | При каждом значимом решении                |
| `docs/BACKLOG.md`          | Отложенные идеи, проблемы, техдолг                                           | Любая сессия                               |
| `docs/FEEDBACK.md`         | Отзывы владельца                                                             | Сессия, получившая отзыв                   |
| `docs/gdd/`                | Дизайн-документ по разделам                                                  | Никто (только владелец)                    |
