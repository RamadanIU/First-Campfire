# Архитектура

Документ описывает, как устроен код и какие правила нельзя нарушать. Он должен соответствовать реальному коду:
изменил устройство — обнови документ в том же PR. Обоснования решений — в [`DECISIONS.md`](DECISIONS.md).

## Технологии

| Что                     | Чем                                                       | Примечание                                                              |
| ----------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| Язык                    | TypeScript (строгий режим)                                | Только «стираемый» синтаксис: Node запускает `.ts` напрямую, без сборки |
| Сборка и dev-сервер     | Vite                                                      | `npm run dev`, `npm run build` → `dist/`                                |
| Отрисовка               | Canvas 2D, собственный лёгкий рендерер                    | Без движка; см. ADR-002                                                 |
| Интерфейс               | HTML/CSS поверх холста                                    | `#ui` в `index.html`                                                    |
| Звук                    | Web Audio, процедурный синтез                             | Появится на этапе 5                                                     |
| Тесты                   | Vitest                                                    | `*.test.ts` рядом с кодом, сценарные — в `tests/`                       |
| Линтер и форматирование | Biome                                                     | `npm run lint`, `npm run format`                                        |
| Скриншоты               | Playwright + Chromium (предустановлены в облачной сессии) | `tools/screenshot.ts`, `tools/e2e.ts` (общее — `tools/browser.ts`); в `package.json` не добавлять. Проверка кадров по пикселям — `tools/png.ts`, `tools/imageChecks.ts` |
| Проверки                | `npm run check` в сессии                                  | GitHub Actions не используется (ADR-011)                                |
| Публикация              | Нет                                                       | GitHub Pages не используется (ADR-011)                                  |

Библиотек времени выполнения нет, и по умолчанию они не добавляются. Нужна зависимость — запись в `DECISIONS.md`.

## Структура каталогов

```
data/            таблицы содержания и баланса (*.json): баланс, ресурсы, земля; позже здания, технологии, черты…
src/
  sim/           СИМУЛЯЦИЯ: состояние мира и системы. Чистая, детерминированная, без браузера
  data/          типы таблиц, их загрузка и проверка
  art/           графика как код: палитра, описания спрайтов, растеризатор, атлас
  render/        отрисовка мира на Canvas 2D: камера, тайлы, спрайты, свет, частицы
  ui/            интерфейс наблюдателя (HTML/CSS): панель, лента событий, карточки, тексты (texts.ts)
  app/           запуск: параметры адресной строки, сцены, игровой цикл, ввод
  main.ts        точка входа
tools/           скрипты Node: дорожная карта, скриншоты, прогоны без графики
tests/           сквозные тесты: архитектурные правила, детерминизм, сценарии
docs/            вся документация проекта (см. docs/PROCESS.md, «Где что лежит»)
```

Направление зависимостей — строго в одну сторону:

```
app → ui, render → art
app, ui, render → sim → data
```

`sim` и `data` не импортируют ничего из `render`, `ui`, `app`, `art`. Это проверяет `tests/architecture.test.ts`.

## Правила, которые нельзя нарушать

### 1. Детерминизм: одно зерно — одна история

- Вся случайность — только через генератор случайных чисел симуляции, состояние которого хранится в мире.
  `Math.random`, `Date`, `performance.now`, таймеры в `src/sim` запрещены (проверяется тестом).
- Время симуляции — это номер тика. Скорость игры меняет число тиков в секунду, но не результат.
- Порядок обхода сущностей фиксирован (массивы, сортировка по id). Результат не должен зависеть от порядка
  вставки в `Map`/`Set`, от кадровой частоты, от размера окна, от положения камеры.
- У каждой системы свой именованный поток случайных чисел, чтобы новая система не сдвигала историю остальных
  сильнее необходимого.
- Тест детерминизма сравнивает хэш состояния двух прогонов одного зерна. Если он упал — ищи источник
  недетерминизма; править сам тест нельзя.
- **Только точная математика.** `Math.sin`, `Math.cos`, `Math.exp`, `Math.log`, `Math.pow`, `**` и подобные
  стандарт разрешает вычислять приближённо, и в разных браузерах последний бит может различаться — этого хватит,
  чтобы истории одного зерна разошлись. В `src/sim` разрешены только `+ − × ÷`, `Math.sqrt`, округления,
  `Math.min/max/abs/imul` и функции из `src/sim/math.ts` (там, например, свой `ln`). Проверяется тестом.
- Уровни детализации (GDD §2.4) не должны менять историю в зависимости от того, куда смотрит камера:
  упрощение определяется правилами симуляции, а не экраном. Решение об этом принимается на шаге 6.11.

### 2. Симуляция отдельно от отрисовки

- `src/sim` ничего не знает об экране. Та же симуляция работает в Node без графики (`npm run sim`) —
  это главный инструмент баланса.
- Отрисовка и интерфейс только **читают** состояние. Никакая игровая логика не живёт в `render`/`ui`.
- Плавность движения — интерполяция в отрисовке между двумя тиками, а не дробные тики в симуляции.
- Симуляция сообщает о происходящем через **журнал событий** (рождение, смерть, открытие, начало стройки…).
  Из него питаются летопись, звук, пузырьки, сценки, статистика.

### 3. Содержание — в таблицах данных

- Ресурсы, здания, технологии, черты, профессии, сценки, числа баланса — в `data/*.json`.
  В коде — механики, а не списки содержания. Критерий: новый ресурс или новое здание существующего типа
  добавляется строкой в таблице, без правки кода.
- Таблицы проверяются при загрузке и тестами: типы полей, обязательные поля, ссылки между таблицами.
  Ошибка в таблице должна называть файл, запись и поле. Как устроено и как добавить запись — раздел «Таблицы данных».
- Идентификаторы в данных — `snake_case` латиницей (`berry_bush`). Названия для игрока — по-русски, отдельным полем.

### 4. Причинность

- У каждого события, решения, постройки, закона хранится **причина** (ссылка на событие или нужду, которые к нему привели).
  Наблюдатель всегда должен иметь возможность получить ответ на вопрос «почему?» (GDD, столп 1).
- Ничего не происходит «по таймеру сценария». Режиссёр событий только сдвигает вероятности.
- Каждый житель ведёт короткий журнал решений (что выбрал и почему) — он нужен для отладки и для поиска
  «нелепых смертей» в прогонах.

### 5. Физичность

- Ресурсы — физические предметы: лежат на тайле, в куче, в хранилище или в руках. Ничего не телепортируется
  и не возникает из воздуха; количество предметов сохраняется (это проверяется тестами-инвариантами).
- Труд виден: у каждого действия есть место, длительность и анимация.

### 6. Каждая технология видна на экране

Технология без видимого проявления (предмет, здание, анимация, деталь одежды, изменение ландшафта) не принимается (GDD §7.5).

### 7. Состояние мира — простые данные

- Мир — обычные объекты, массивы и типизированные массивы, которые целиком сериализуются (сохранение, хэш, снимки
  для таймлапса). Без классов с поведением внутри состояния, без замыканий, без ссылок на DOM.
- Ссылки между сущностями — по числовым id, а не по указателям.
- У сохранения есть номер версии формата (`SAVE_VERSION`). **Любое изменение устройства мира поднимает версию** —
  тест формы мира в `src/sim/save.test.ts` не даст забыть. С этапа 5 старые сохранения обязаны открываться
  (переносы в `MIGRATIONS`). Подробно — раздел «Сохранения».

### 8. Воспроизводимость экрана

- Любое состояние игры достижимо адресной строкой: `?scene=…&seed=…&ticks=…&cam=x,y&zoom=…&ui=0`; отладка мира —
  `debug=1` (пути жителей линиями, щелчок отправляет жителя), `debug=needs` (шаг 1.4: полоски сытости, жажды и
  здоровья над головой, с 1.5 — и сна; в панели — кто что делает и кто от чего умер; слова — через запятую),
  `debug=mind` (шаг 1.8: план и журнал решений выбранного жителя с оценками вариантов), `go=x,y`
  (житель 1 идёт на тайл с сотворения мира, до промотки `ticks=` — путь воспроизводим адресом), `food=15@955` (шаг 1.8:
  на тике 955 по дороге к `ticks=` сытость жителя 1 становится 15 — голод прерывает работу), `light=0` (шаг 1.5:
  мир без света времени суток — как днём; для сравнения кадров пиксель в пиксель), `warmth=15@3720` (шаг 1.12: то же,
  что `food=`, для тепла — мёрзнет), `bubbles=0` (шаг 1.12: без пузырьков мыслей).
  Это основа скриншотов и отчётов об ошибках. Новая сцена или режим — значит, новый параметр.
  Состояния, которые зависят от хранилища браузера (меню с сохранённым миром, испорченное сохранение), задаёт
  отладочный параметр `slot=` (раздел «Сохранения»).
- Сцены регистрируются в `src/app/scenes.ts`. Отладочные сцены (галерея спрайтов, палитра, песочницы) — тоже сцены.
  Параметры конкретных сцен тоже живут в `src/app/params.ts` (например, `sprite=` галереи; `zoom=` — ступень
  камеры `0.5`, `1`, `2`, `4` и `cam=x,y` — куда она смотрит, в тайлах; раздел «Камера»).
- Страница сообщает о готовности через `window.__fc.ready` и об ошибках через `window.__fc.errors` —
  на это опирается `tools/screenshot.ts`. Сцена `world` кладёт в `window.__fc.world` зерно, тик, хэш, откуда мир,
  тик последнего автосохранения и мир таким, каким сцена его открыла (`opened`: тик и хэш до первого тика —
  мир сразу идёт дальше), жителей (`villagers()`: тайл, шаг, действие, цель, пройденный путь, нужды и здоровье) — на это опирается
  `tools/e2e.ts` (не читает мир с экрана); камеру — в
  `window.__fc.camera` (ступень, центр, видимая часть, `worldAt(x, y)` — точка мира под точкой страницы).
  Время отрисовки живых кадров — `window.__fc.renderMs` и `firstRenderMs` (`npm run shot -- --frame-time`,
  раздел «Проверка кадров»).

### 9. Производительность — с первого дня

Целевые бюджеты (уточняются ревизиями этапов):

| Показатель                              | Цель                          |
| --------------------------------------- | ----------------------------- |
| Тик симуляции при 100 жителях           | ≤ 1 мс                        |
| Тик симуляции при 1500 жителях          | ≤ 8 мс (иначе ×20 невозможна) |
| Кадр отрисовки                          | ≤ 16 мс на среднем компьютере |
| Прогон без графики: 100 лет, 40 жителей | ≤ 30 с на зерно               |

Меряй, а не угадывай. Замеры — в отчёте шага и в `STATUS.md`. Время тика без графики меряет каждый прогон
`npm run sim` (среднее, 99 % тиков, худший); точнее всего — на одном потоке: `npm run bench` (3 мира × 200 лет,
тиков в секунду, игровых лет в секунду и хэш мира на каждое зерно). См. «Прогоны без графики».

**Карта.** `createWorld(seed)` строит карту генератором (`world.map`, `world.objects`) — 64×64 за ≈ 3 мс (95 % зёрен —
≤ 5 мс). По ходу жизни мира карта меняется пока в одном месте: на середине стоянки появляется очаг (шаг 1.9). Гарантии генератора —
`tests/mapgen.test.ts` на зёрнах 1…100; устройство и решения — ADR-019.

**Жители** (шаг 1.3, ADR-021). После карты `createWorld` ставит двоих — мужчину и женщину — у места для стоянки
(`findCampSite`) и пишет в журнал их приход (`villager_arrived`, причина — сотворение мира). Система `villagers` (четвёртая
в `SYSTEMS`, потоки случайности `villagers` и `minds`) каждый тик: запоминает позицию прошлого тика, продолжает шаг (тайл травы
за 4 тика, песок медленнее, диагональ — в √2 дольше), на тайле решает, что дальше: отдохнуть, пойти к свободному тайлу
у дома, сделать следующий шаг пути, подождать или обойти того, кто стоит на пути. Двое никогда не стоят в одном тайле
(тайл и тайл текущего шага заняты). Гарантии — `tests/villagers.test.ts`: обход реки, недостижимая цель, инвариант «не в
воде, не в дереве, не вдвоём» на 5 000 тиков 20 зёрен, детерминизм с сохранением посреди шага. Маленькие карты для
сценариев рисуются строками — `tests/scenario.ts` (`mapFromRows`, `worldOn`, `meadow`). Скорость поиска пути —
`npm run bench:path` (`tools/pathBench.ts`).

**Нужды** (шаг 1.4, ADR-023). Сытость и жажда — шкалы 0–100 (100 — нужды нет), здоровье — 0–100. Система `life`
(третья в `SYSTEMS`, перед жителями) каждый тик опускает шкалы по `data/balance.json` (`needs`), пишет
`need_ran_out`, когда шкала дошла до нуля, отнимает здоровье, пока нужда на нуле, и пишет смерть `villager_died` с
причиной (событие нужды, опустевшей первой) и признаками «еда/вода в досягаемости»; умерший уходит из мира. Что делать,
решает разум (`minds.ts`, `choose`): отдыхающий раз в `ai.thinkTicks` сравнивает отдых с едой и питьём — нужда² ×
доступность, с лёгкой случайностью; победила нужда — идёт к ближайшему по пути месту сбоку от куста с ягодами или от
воды (`findNearest`), встаёт лицом к источнику и ест горстями (ягоды убывают с куста, `takeFood`) или пьёт глотками,
пока не утолит. Гарантии — `tests/needs.test.ts`: 20 зёрен × 7 суток без нулей, смерть от голода и от жажды с причиной,
ни одной смерти при доступной еде и воде (30 суток), еда и питьё, выбор, встреча лоб в лоб, детерминизм.

**Сон** (шаг 1.5, ADR-025). Третья шкала: падает за 1,5 суток бодрствования, во сне на земле возвращается (0,5 пункта за
тик — половина лежанки), на нуле не убивает, а валит с ног — обморок (`villager_fainted`, причина — событие
`need_ran_out` сна), лежит до `sleeping.faintWakePoints`. Желание спать — `sleepWish` в `minds.ts`: ночью прибавка
перевешивает отдых, поэтому с наступлением ночи ложатся где стоят и спят до рассвета; днём дремлет только невыспавшийся.
Спящий думает раз в `ai.thinkTicks` и встаёт, когда разум выбрал что-то другое и оно полезнее желания спать на
`ai.sleepHold`: отдых (выспался и уже не ночь) или еду и питьё. Идущий (кроме приказа) так же думает в пути и ложится по
дороге, если сон перевесил его план (с 1.8 — общий механизм планов, ниже). Гарантии — `tests/sleep.test.ts`: 20 зёрен
× 3 суток — ночью спят ≥ 80 %, днём не спят; просыпается от жажды; ложится в пути ночью; обморок с причиной; детерминизм.

**Разум и планы** (шаг 1.8, ADR-028, GDD §2.3). Всякое занятие — описание в `ACTIVITY` (`src/sim/minds.ts`): нужда,
функция полезности (нужда × характер × контекст; доступность источника — при поиске), упрямство и **план** — шаги:
отдых — постоять → прогуляться (и снова), сон — спать, еда и питьё — дойти → есть/пить, работа — дойти до веток →
поднять → набрать ещё → донести до кучи → сложить, приказ — дойти. У жителя `plan` (занятие, оценка при выборе, когда,
шаги впереди); `action` — шаг, который идёт сейчас; закончился шаг — `nextStep` начинает следующий; шаги кончились —
план выполнен, дальше отдых; не вышло (куст обобран, предмет унесли, нет пути или места) — план «не вышел», отдых.
**Раздумье** — раз в `ai.thinkTicks` (со сдвигом по id) за любым делом: стоящий — в свой момент, идущий — на первом
шаге после него (`thought`, `thinkingDue`); `reconsider` ищет лучшее, не ища заново то, что уже делается. **Упрямство**
(`Hold`, `holdOf`): еда, питьё, работа — `firm`: бросить их можно только ради того, что полезнее оценки при выборе (или
нужды сейчас, если выросла) в 1 + `ai.keepMargin` раз; сон — `fresh`: держится желанием спать сейчас + `ai.sleepHold`;
отдых — `loose`: уступает всему лучшему; приказ — `fixed`. Ноша держится, только пока план — работа. Каждое решение —
в **журнал решений** жителя (`log`, последние `ai.logSize`): когда, почему (выбрал, сделано, не вышло, приказ, обморок),
что бросил и какой порог перебил, все варианты с оценками; `debug=mind` показывает его для выбранного жителя. Гарантии —
`tests/plans.test.ts`: с ношей и сытостью 60 донесёт, с 15 — бросит и пойдёт есть; нет «дёрганья» (10 миров × 10 суток);
журнал объясняет любой поступок (план — последнее решение, шаг — из плана, выбор — с причиной); план работы по шагам.

**Предметы** (шаг 1.7, ADR-027). Ресурс — стопка: на тайле (`world.items.list`: на земле — `place: 'ground'`, в куче у
стоянки — `'pile'`) или в руках (`villager.load`, одна стопка). На тайле — одна стопка одного ресурса, не больше его
`stack`; кладут только на проходимую землю без объекта. Стоянка — `world.camp` (середина — место для стоянки, место
кучи — на `items.pileOffset` южнее); куча — тайлы вокруг места кучи (`pileTiles`), заполняется от середины. Система
`litter` (последняя в `SYSTEMS`, поток `items`) роняет ветки с деревьев (`litter` в `data/objects.json`) на соседний свободный
тайл; охапками (не ближе `items.litterSpacing` к другой стопке), не больше `items.maxLoose` стопок на земле — при пределе
самая старая сгнивает (шаг 1.10, `items.rotted`). Работа —
вариант выбора разума `haul` (`ai.haulUtility` × доступность ближайшей стопки, для которой в куче есть место) — план
(с 1.8): идти (`walk`/`fetch`) → подобрать (`pick_up`) → набрать охапку (ещё `fetch`, пока руки не полны и рядом есть)
→ нести (`walk`/`carry`) → сложить (`put_down`). Ноша держится, только пока план — работа: иначе житель кладёт её, где
стоит (`dropLoad`), в том числе умирая. **Закон сохранения**: стопки на тайлах + ноши + сожжённое (`items.burned`, шаг 1.9) + сгнившее (`items.rotted`, шаг 1.10) = `items.made` (только падение создаёт предметы, только огонь и гниль их забирают).
Гарантии — `tests/items.test.ts`: все правила предметов каждый тик 10 000 тиков на 5 зёрнах, куча растёт (сценарий на
опушке и 20 миров), ноша не теряется (приказ, ночь, смерть), сохранение посреди переноски, падение веток, полная куча.

**Костёр** (шаг 1.9, ADR-029, GDD §7.4, §13.3). Очаг — объект карты `campfire` на середине стоянки (`world.camp`), его
строит первый, кто разводит огонь (цветы под ним вытаптываются). Огонь — `world.fire`; система `fire` (после жителей) сжигает
`fire.fuelPerDay` охапок сезона в сутки (охапка — одна ветка: весна–осень 1, зима 3), без дров — `fire_out` (правило
`fuel`). Разум (`minds.ts`): `kindle` — развести, когда не горит и в куче ≥ `fire.kindleBranches`; `stoke` — подложить, чем
меньше дров, тем нужнее, а вечером — чтобы хватило до утра; оба — план «дойти до дров в куче (с края) → взять → донести до
огня → развести/подложить», хлопочет один. `sit` — вечером и ночью у горящего огня (досуг: начатое ради него не бросают),
места — прямо слева и справа, потом рядом, лицом к огню. Сон — план «лечь у огня → спать» (если до огня не дальше
`fire.sleepWalkTiles`). Работа, что затянется до вечера, дешевле (`eveningWork`); пустая куча делает её дороже
(`woodNeed`). Тепло — `warmthAt` (для 1.10). Отрисовка — `src/render/fire.ts`: тёплые кольца света по темноте, пламя
поверх света суток, искры, дым. Гарантии — `tests/fire.test.ts`: ночью оба спят у огня, вечером сидят (сценарий и 20 миров),
без дров гаснет (весной за 3 суток на 3 ветках, зимой — за сутки), с ветками за год не гаснет (сценарий и 20 миров),
очаг и причина-решение, дрова с края кучи; `src/sim/fire.test.ts` — огонь, предел, тепло, вечер.

**Тепло, погода, сезоны** (шаг 1.10, ADR-030, GDD §3.2, §4.2). Погода — `world.weather`, система `weather` (вторая, после
календаря; поток `weather`). Температура воздуха — сезон + фаза суток + погода (`weather` в `data/balance.json`); у горящего
огня теплее на `fire.heat` × `warmthAt` (`feltAt`). **Тепло** — четвёртая шкала: следует температуре тайла жителя (ниже
`needs.warmth.comfort` убывает, выше прибывает), на нуле — обморожение и смерть «холод» (система `life`). Разум: `warm` —
греться у огня (как «сидеть у огня»), холодному развести огонь полезнее, в дождь развести нельзя; в холод работают не дальше
`coldReach`, перед далёким походом греются (`precaution`), поход, на который не хватит тепла, ждёт; морозной ночью спать
идут к огню издалека (`fire.coldSleepWalkTiles`); зимой вечер раньше (`fire.eveningTicks` по сезонам). **Дождь** —
`fire.rainOutTicks` тиков подряд — гасит костёр (правило `rain`), мокрые дрова остаются в очаге. **Еда по сезонам** —
`harvest.seasons`: малина весной–осенью (с 1.11a зимой пуста — урожай осыпается, ниже), лещина (орехи) и коренья — осенью и зимой
(генератор ставит их у опушек последним шагом, `map.forage`). Гарантии — `tests/warmth.test.ts`: без костра зимой оба
умирают от холода с цепочкой причин, с костром зимуют и спят у огня, 20 миров × год — пара жива, дождь гасит и в дождь не
развести, короткий дождь не гасит, зимой не едят ягоды, едят орехи и коренья, замёрзший идёт греться; `src/sim/weather.test.ts`
— температура, смена погоды по сезонам, детерминизм; `src/sim/needs.test.ts` — шкала тепла.

**Урожай раз в год** (шаг 1.11a, ADR-031, GDD §3.2). Система `harvest` (`src/sim/harvest.ts`, после погоды, до жизни; без
случайности) раз в сутки, в начале дня: в сезон созревания (`harvest.ripens` в `data/objects.json`) на объекте прибавляется доля
годового урожая `harvest.rations ÷ дней в сезоне` (съеденное не возвращается); в первый день сезона созревания и в первый день
сезона вне `harvest.seasons` несобранное осыпается (запас 0, состояние «пусто»). Малина зреет весной, лещина и коренья —
осенью. Новый мир получает урожай своего первого дня (`setCrops`; тесты, переставляющие часы рукой, зовут его же).
Тестам, которым нужна еда «без конца», — `plenty(world)` из `tests/scenario.ts` каждый тик. Житель, подойдя к еде,
пишет событие `food_found` (расстояние от середины стоянки) — показатели «Поход за едой / за ягодами весной, летом,
осенью». Разум помнит «далеко» (`villager.tooFar`): поиск, который не нашёл ничего стоящего, не повторяется
`ai.farRetryTicks`. Гарантии — `src/sim/harvest.test.ts` (доли, осыпание, «пуст до следующего урожая», лещина осенью) и
`tests/harvest.test.ts` (ряд кустов — каждый раз дальше; 20 миров × 5 лет — последний поход года дальше первого;
обобранные кусты к следующему году полны; память «далеко»).

**Память, разведка, запас** (шаг 1.11b, ADR-032, GDD §2.3, §13.2). `src/sim/memory.ts`: житель видит на `ai.sightTiles`
вокруг и осматривается (`look`) на каждом новом тайле; разведанная земля — клетки `ai.cellTiles` (`villager.seen`, клетка
разведана, когда была в виду целиком), увиденная еда — `villager.foods` (`Known`: объект, когда видел, была ли еда). Еду ищут
только среди того, во что житель **верит** (`believesFood`: видел с едой или куст с тех пор созревал — урожай идёт по
календарю); правда о карте — `searchSource(…, { known: false })` (признак смерти «еда была досягаема»). Нет известной еды —
занятие `scout` к ближнему голому тайлу неразведанной клетки (`searchFrontier`); увидел новую еду — план кончен. Сидящие у
огня делятся памятью (`share`). Запас еды — квадрат `camp.store` у кучи веток (`pileTiles(world, 'nuts')`, еда — только туда,
ветки — только в кучу); занятие `store` собирает в руки то, что хранится (`keeps`: `spoilDays ≥ stores.keepDays` — орехи),
действием `pick` и несёт в запас (`food_stored`); едят из запаса (`eat_stored`) зимой или когда кустов с едой не знают
(`searchFood`). Еда портится (`Stack.spoils`, система `spoil` в начале суток, `items.spoiled`); инвариант предметов
учитывает `picked` и `eaten`. Поиск к немногим известным местам — A* (`towards` у `findNearest`). Отладка — `debug=memory`
(неразведанное под тёмной сеткой, известная еда — метки). Тестам, которым память мешает, — `knowAll(world)`, запас —
`fillStore(world)` (`tests/scenario.ts`). Гарантии — `src/sim/memory.test.ts`, `tests/memory.test.ts`.

**Тик.** `world.tick` — сколько тиков уже прошло; тик 0 — момент сотворения (рассвет первого дня весны первого года).
`stepWorld` сначала увеличивает `tick`, потом вызывает системы в порядке `SYSTEMS` — системы видят новый тик.
Порядок систем — часть правил мира: переставлять нельзя, новая система добавляется осознанно.

**Как добавить систему.** Файл `src/sim/systems/<имя>.ts` экспортирует объект `System` (`id`, `step(world)`).
Её состояние — поле в `World` (простые данные) с начальным значением в `createWorld`. Если нужна случайность —
новое имя в конец `RNG_STREAMS` и `world.rng.<имя>`: поток выводится из пары «зерно + имя», поэтому новая система
не меняет числа, которые получают остальные. Затем систему ставят в `SYSTEMS` и пишут тест. Новое поле в мире
меняет его устройство — подними `SAVE_VERSION` и обнови форму мира в `src/sim/save.test.ts` (упавший тест
напечатает новую форму и подскажет порядок; раздел «Сохранения»).

**События и причины.** Каждое событие — `{ id, tick, type, cause, …данные }`. Причина (`cause`) — либо закон
мира (`{ kind: 'rule', rule: 'calendar' }`), либо другое событие журнала (`{ kind: 'event', event: id }`).
Новые виды причин (нужда, решение жителя) добавляются в тип `Cause`. Системы узнают о случившемся в этот тик
через `eventsThisTick(world, тип)` и ссылаются на него как на причину своих событий. Журнал пока хранит всю
историю (≈ 6–7 событий в игровой день); ограничение и архив — когда понадобится (см. `BACKLOG.md`).

**Случайность.** Функции `rng.ts` по возможности тратят одинаковое число выборок (например, `chance` тянет число
даже при p = 0), чтобы подстройка вероятности не сдвигала остальной поток. Эталонный тест в `rng.test.ts`
фиксирует первые числа генератора: если он упал — изменился алгоритм, а значит, все истории.

## Таблицы данных

Появились на шаге 0.5 (ADR-005, ADR-014). Содержание и числа баланса лежат в `data/*.json`; код описывает,
**что** в таблице может быть, читает её и проверяет. Посмотреть таблицы такими, какими их загрузила игра:
`?scene=data`.

| Файл | Что в нём |
|------|-----------|
| `data/balance.json` | Числа времени, движения и жизни (GDD §2.1, §13.1): сутки, сезон, фазы суток, скорость ходьбы, возрасты; с 1.4 — потребности (`needs`), еда и питьё (`eating`), выбор действия (`ai`); с 1.7 — предметы (`items`: куча, подбор и укладка, охапка, падение веток) и работа (`ai.haulUtility`, `ai.workRetryTicks`) |
| `data/resources.json` | Ресурсы (GDD §5.2): id, название, категория, эпоха, стопка, срок порчи, спрайт; с 1.7 — как стопка выглядит в куче (`pile`) и в руках (`carry`) |
| `data/terrain.json` | Типы земли: проходимость, скорость относительно травы, вид (`TERRAIN_LOOKS` из `src/art/terrain.ts`) |
| `data/objects.json` | Объекты карты (шаг 1.1): название, спрайт, проходимость, состояния (первое — начальное), где их ставит генератор (`place`: лес, опушка, россыпь, луг) и как часто (`weight`); с 1.7 — что с объекта падает (`litter`: ресурс, до скольких, раз в сколько суток); с 1.4 — еда на объекте (`harvest`: ресурс, рационов, состояние «всё собрано»; `null` — нечего собрать). Числа карты — раздел `map` в `balance.json` |
| `data/names.json` | Имена (шаг 2.1, GDD §8.6): культурный набор слогов — корни (`roots`, с большой буквы), окончания мужских и женских имён (`male`, `female`), сочетания, которые не даются (`skip`). Сейчас один набор — «Народ первого костра»; имена берутся из первого |
| `src/data/schema.ts` | Маленькая библиотека схем: типы полей, проверка, сообщения об ошибках, ссылки между таблицами |
| `src/data/tables.ts` | **Схемы всех таблиц** с пояснением каждого поля, типы (`Balance`, `Resource`, `Terrain`), `loadTables` |
| `src/data/index.ts` | Загрузка: `DATA` — проверенные и замороженные таблицы; `RAW_TABLES` — файлы как есть (для тестов) |
| `src/app/dataRefs.ts` | Проверка ссылок таблиц на спрайты и виды земли (`checkDataRefs`) — `src/data` не видит `src/art` |
| `src/app/dataScene.ts` | Сцена `data`: ресурсы со значками, земля, баланс с пояснениями из схемы |

**Как читать данные в коде.** `import { DATA } from '../data/index.ts'`: `DATA.balance.time.ticksPerDay`,
`DATA.resources.get('berries').spoilDays`, `DATA.terrain.records` (в порядке файла), `DATA.resources.has(id)`.
`get` с неизвестным id бросает ошибку — это ошибка в коде, а не в данных. Таблицы заморожены: менять их нельзя,
состояние мира хранится в `World`. Симуляция берёт из таблиц только числа и списки содержания; списки, от которых
зависит механика (фазы суток, сезоны, категории ресурсов), — в коде.

**Единицы.** В таблицах — игровые единицы, понятные человеку: сутки, годы, сезоны, проценты, множители (×1,1).
Перевод в тики — в коде (`calendar.ts`). Еда считается в **рационах** (еда взрослого на сутки, GDD §13.2);
стопка — сколько лежит на тайле и уносят руки (GDD §5.1), поэтому отдельного веса нет.

**Правила таблиц** (их проверяет загрузка):

- идентификаторы — `snake_case` латиницей и не повторяются; названия для игрока — по-русски, полем `name`;
- каждое поле записи обязательно; «нет значения» — явный `null`, если схема его разрешает (`"spoilDays": null` —
  не портится), а не пропуск поля; поле, которого нет в схеме, — ошибка (скорее всего, опечатка);
- одна запись — одна строка файла (для `data/**` в `biome.json` ширина строки 220 знаков — с шага 1.4).

**Ошибка в таблице** называет файл, запись и поле, говорит, что ожидалось и что найдено, и подсказывает
опечатку. Проверка не останавливается на первой ошибке — перечисляет все:

```
Ошибки в таблицах данных (2):
  • data/resources.json · запись «berries» · поле «stack»: ожидается целое число от 1 до 1000, получено "много"
  • data/resources.json · запись «nuts» · поле «spoilDay»: лишнее поле — может быть, «spoilDays»? Известные поля: …
```

Где её видно: в `npm test` (любой тест, который загружает данные, и `src/data/tables.test.ts`), в браузере —
красное окно «Игра не запустилась» вместо игры, в `npm run shot` — кадр падает. Ссылка на несуществующий спрайт
или вид земли ловится `tests/data.test.ts` и при запуске игры (предупреждение поверх сцены).

### Как добавить запись

1. Добавить строку в таблицу, например в `data/resources.json`:
   `{ "id": "acorns", "name": "Жёлуди", "category": "food", "era": 0, "stack": 5, "spoilDays": 12, "sprite": "acorns" }`.
2. Если нужен новый значок — файл `src/art/sprites/acorns.ts` (вид `item`, 10×10, см. `docs/ART.md`, «Предметы»).
3. `npm test` — проверит запись, ссылку на спрайт и то, что у каждого спрайта-предмета есть ресурс.
4. `?scene=data` — ресурс уже в списке, код не менялся.

### Как добавить поле или таблицу

- **Новое поле** существующей таблицы: описать его в схеме в `src/data/tables.ts` (тип, диапазон, `doc` —
  пояснение по-русски, `unit` — единица) и дописать значение в **каждую** запись таблицы. Тип TypeScript
  выводится из схемы сам; сцена `data` покажет новое число баланса с пояснением без правки сцены.
- **Новый раздел баланса** — `obj({...}, { doc: 'Название (GDD §…)' })` в `balanceSchema` и раздел в
  `data/balance.json`.
- **Новая таблица**: файл `data/<имя>.json`; схема — `table({ id: id(), … })` в `src/data/tables.ts`; строка в
  `TABLES` (файл и схема) и поле в `GameData`/`loadTables`; импорт файла в `src/data/index.ts`; тест испорченной
  записи в `src/data/tables.test.ts`. Ссылка на запись другой таблицы — `ref('resources')`; на то, что определено
  вне данных, — `external(вид, 'название')` и каталог этого вида в `src/app/dataRefs.ts`.
- **Правило про запись целиком** (сумма долей, согласованность полей) — опция `check` у `obj`/`table`: функция
  возвращает текст ошибки или `null`; вызывается, только если сами поля в порядке.

## Прогоны без графики

Появились на шаге 0.6 (ADR-015). Главный инструмент баланса (GDD §14.1, принцип 5): много миров проигрываются
в Node без экрана, итог — таблица и файлы. Симуляция та же, что в браузере.

```
npm run sim                                         # зёрна 1..100, по 10 лет
npm run sim -- --seeds 1..20 --years 50             # другие зёрна и срок
npm run sim -- --seeds 1,5,7 --years 2 --threads 1 --out out/sim-test
npm run sim -- --load мир.json --years 5            # мир из сохранения — ещё 5 лет
npm run bench                                       # скорость: 3 мира × 200 лет на одном потоке
npm run bench:path                                  # скорость поиска пути (A*) на картах зёрен 1..20
npm run sim -- --help                               # справка
```

Параметры: `--seeds` (`1..100`, `1,2,5`, `1..10,50`), `--years N` (целые игровые годы), `--load файл` (продолжить
мир из сохранения; см. ниже), `--threads N` (по умолчанию — по числу ядер, не больше числа миров), `--out папка`
(по умолчанию `out/sim`; `out/` не в git). Код выхода: 0 — все миры дожили до конца, 1 — какой-то мир упал с
ошибкой (остальные досчитываются), 2 — ошибка в параметрах или сохранение не открывается.

**Из сохранения (`--load`).** Продолжается один мир — тот, что в файле (сохранение из игры: «Сохранить в файл»),
ещё на `--years` лет, то есть N × 4 800 тиков от тика сохранения; поэтому вместе с `--seeds` нельзя. Файл
проверяется до запуска потоков. Если сохранение сделано посреди года, первый и последний срезы в `years.csv`
неполные (`from_tick`/`to_tick` это показывают). Если таблицы данных изменились после сохранения, команда
предупредит (мир живёт по текущим). Так воспроизводится мир из браузера: «житель утонул на 34-м году» →
сохранение в файл → `npm run sim -- --load …` с полной статистикой.

| Модуль | Что делает |
|--------|------------|
| `src/sim/metrics.ts` | Список показателей `METRICS` — что считать в каждом мире |
| `src/sim/stats.ts` | Виды показателей и их запись: итог за прогон и срез за каждый год. Детерминирована, в мир не пишет |
| `tools/sim.ts` | Команда: раздаёт зёрна потокам по одному, показывает прогресс, пишет файлы, печатает таблицу |
| `tools/sim/worker.ts` | Поток: разогрев, цена отсчёта часов, прогон присланных миров |
| `tools/sim/run.ts` | Один мир: `runWorld({ seed, years, start? })` — новый или загруженный (`start`); шаги, запись показателей, замер каждого тика; ошибка мира не роняет прогон |
| `tools/sim/timing.ts` | Замер тика: среднее, 99 % (гистограмма), худший; вычитание цены самого замера |
| `tools/sim/report.ts` | CSV, сводка JSON, таблица в консоли; `TIMING_COLUMNS`, `dropColumns` |
| `tools/sim/args.ts` | Разбор и проверка параметров, справка |

### Что получается

- **Таблица в консоли**: по каждому показателю — среднее, минимум и максимум по мирам; в скобках — зерно мира с
  этим значением (его можно открыть и посмотреть). Ниже — время тика и скорость мира. Если миров не больше 10,
  выше таблицы — строка на каждый мир с хэшем. **Отпечаток прогона** — один хэш всех миров: меняется, только если
  изменилась история хотя бы одного (удобно сравнивать версии кода).
- **`worlds.csv`** — строка на мир: `seed, status (ok/error), years, from_tick, ticks, hash`, показатели за весь
  прогон, затем столбцы времени. `from_tick` — с какого тика начат прогон (0, или тик сохранения при `--load`),
  `ticks` — каким тиком закончился, `years` — сколько целых лет прожито в этом прогоне.
- **`years.csv`** — строка на мир и год: `seed, year, from_tick, to_tick`, показатели **этого года**, время тика за год.
  Из него строятся кривые («население по годам»).
- **`summary.json`** — команда и параметры (`params.load` — сохранение, если было), машина, время и скорость
  (тики — прожитые в этом прогоне), отпечаток, по каждому показателю среднее/мин/макс с зёрнами (`metrics`), те же
  числа по календарным годам (`years`), время тика, упавшие миры с местом ошибки.

CSV — стандартный: разделитель запятая, дробная часть через точку, дробные числа округлены до 4 знаков
(Google Таблицы открывают сразу; в русском Excel — «Данные → Из текста», разделитель «запятая»).

**Воспроизводимость.** Всё, кроме времени, детерминировано: одни параметры — побайтно те же файлы, при любом числе
потоков. Столбцы времени перечислены в `TIMING_COLUMNS` и стоят в конце строки. Это проверяет `tests/sim.test.ts`:
настоящая команда запускается трижды (дважды на трёх потоках, раз на одном), CSV сравниваются без столбцов времени.

### Как добавить показатель

Одна строка в `METRICS` (`src/sim/metrics.ts`). Обычно — из события журнала:

```ts
count('deaths_cold', 'Умерли от холода', 'villager_died', (e) => e.cause === 'cold'),  // сколько событий
sum('berries_eaten', 'Съедено ягод', 'food_eaten', (e) => (e.food === 'berries' ? e.amount : null)),
mean('food_trip', 'Поход за едой, тайлов', 'food_found', (e) => e.distance),            // среднее
max('oldest', 'Самый старый умерший, лет', 'villager_died', (e) => e.age),             // также min
gauge('population', 'Население (на конец года)', (world) => world.villagers.length),    // из состояния мира
share('time_work', 'Доля времени: работа', (v) => timeOf(v) === 'work'),                // доля тиков жителей
```

- `count`, `sum`, `mean`, `max`, `min` смотрят события одного типа (`'any'` — все события); фильтр или значение
  `null` исключает событие. Тип события проверяется TypeScript: поле `e.distance` должно быть у этого события.
- `gauge` читает состояние мира **на конец каждого года** и на конец прогона.
- `share` (1.13, ADR-035) после **каждого тика** смотрит на всех живых жителей и считает, скольких выбрала проверка:
  итог — доля «выбранные тики жителей / все тики жителей» (0…1), `null`, если за период никто не жил. Так считаются
  доли времени суток (`time_work`, `time_sleep`, `time_leisure`, `time_meals`; разбивка — `timeOf` в `metrics.ts`:
  работа — занятия `haul`, `kindle`, `stoke`, `store`, `scout`; сон — действие `sleep`; остальное — еда и досуг).
  Проверка — чистая функция жителя, дешёвая: она идёт каждый тик.
- Год в срезе — тики `from_tick + 1 … to_tick` (4 800 шагов) и состояние после них; событие на самом рубеже
  (тик 4 800) относится к закончившемуся году. Первый срез включает и рождение мира (тик 0). Запись, начатая у
  мира, который уже жил (загружен из сохранения), события его текущего тика не считает — их сделал прошлый шаг;
  поэтому статистика, разрезанная на любом тике, складывается в ту же, что у непрерывного прогона.
- `null` в итоге — «нечего сообщить» (среднее, максимум, минимум без единого события); в CSV — пустая ячейка,
  в сводке такие миры не участвуют.
- id — `snake_case`, это имя столбца: не переименовывай и не переиспользуй под другой смысл. Повтор id или пустое
  название — ошибка при запуске (`checkMetrics`, тест в `src/sim/stats.test.ts`).
- Нужен показатель, который не выражается ни событием, ни состоянием на конец года (например, среднее за год по
  каждому дню), — новый вид в `src/sim/stats.ts` с тестом; список видов — тип `MetricKind`.

Показатели записываются **снаружи мира**, как его смотрит отрисовка: `createStats(world, METRICS)`, затем
`recordTick(stats, world)` после каждого `stepWorld`, в конце `finishStats`. Мир от этого не меняется — новый
показатель не меняет ни историю, ни хэш, ни сохранения. Запись читает только новые события журнала, поэтому
переживёт и будущее ограничение журнала.

### Как читать время тика

- **Среднее** — сумма времени тиков / число тиков. Из каждого тика вычтена цена самого замера (`performance.now()`
  ≈ 50 нс — у пустого мира это шестая часть тика), измеренная в каждом потоке.
- **99 % тиков не дольше** — надёжная оценка «тяжёлых» тиков (гистограмма, погрешность ≤ 4 %). У пустого мира
  тяжелее всего ночные тики (летает рой светлячков) и тики с событиями (смена фазы суток, вылет роя).
- **Худший** — чаще всего пауза движка JavaScript (сборка мусора), а не игра: смотри на него как на рывок.
- Потоки делят ядра и мешают друг другу, первые миры потока ещё «разогреваются» — поэтому время тика честнее всего
  меряет `npm run bench` (один поток). Скорость мира — игровых лет в секунду **чистого счёта** тиков; общая скорость
  прогона в первой строке итога — по часам, со всеми накладными расходами и всеми потоками.

## Сохранения

Появились на шаге 0.7 (ADR-016). Мир сохраняется текстом и продолжается с того же места — история не меняется:
5 000 тиков → сохранить → загрузить → ещё 5 000 дают тот же хэш, что 10 000 подряд (`tests/determinism.test.ts`).

### Формат

Одна строка JSON: заголовок и мир как есть (он и так простые данные).

```
{"format":"first-campfire/world","version":1,"seed":7,"tick":9000,"hash":"…","data":"…","world":{…}}
```

| Поле | Что это |
|------|---------|
| `format` | Метка «это сохранение Первого костра»; без неё файл — чужой |
| `version` | Версия формата `SAVE_VERSION` |
| `seed`, `tick` | Зерно и тик мира — для меню (сверяются с самим миром) |
| `hash` | Отпечаток мира (`hashState`): не совпал — сохранение повреждено |
| `data` | Отпечаток таблиц `data/*.json` на момент сохранения: другой — только предупреждение, мир живёт по текущим |
| `world` | Мир (`World`) |

- **Типизированные массивы** (слои карты) пишутся как `{"$typed":"Uint16Array","base64":"…"}` (байты
  little-endian) и восстанавливаются при загрузке обходом разобранного JSON (не reviver'ом `JSON.parse`: он
  вызывается для каждого значения журнала и втрое медленнее). Ключ `$typed` в состоянии мира не использовать.
  Тот же JSON без заголовка — `toSaveJson` / `fromSaveJson` (так тесты детерминизма гоняют мир «через JSON»).
- **NaN и бесконечность** JSON не переносит — `saveWorld` останавливается с именем поля (это ошибка симуляции).
  Не простые данные (Map, класс, функция) — тоже ошибка, с путём (её находит `hashState`).
- **`loadWorld(text)` не бросает исключений**: мир (и предупреждения) или причина — `empty`, `not_save`, `damaged`,
  `too_new`, `too_old` — с текстом для игрока по-русски и подробностями для отчёта об ошибке.
- Размер и скорость (Node, шаг 1.1): новый мир — 75 КБ (карта: слой объектов 21 КБ, список объектов 47 КБ,
  земля 5 КБ), через 10 лет — 155 КБ, через 200 лет — 1,75 МБ (дальше растёт журнал событий); сохранение
  200-летнего мира ≈ 31 мс, загрузка ≈ 39 мс; нового — 2 мс / 2 мс.

### Версия формата и форма мира

Старое сохранение не должно открываться «почти подходящим» к новому коду — поэтому **любое изменение устройства
мира поднимает `SAVE_VERSION`** (`src/sim/save.ts`). Следит за этим тест `src/sim/save.test.ts`: он снимает
«форму» мира за первый год (все пути с видами значений — `events.list[].tick: number`, — и значения полей `type` и
`kind`) и сравнивает с `CURRENT_SHAPE`. Добавил систему, поле или тип события — тест упадёт и напечатает новую
форму. Тогда в том же шаге:

1. поднять `SAVE_VERSION`;
2. заменить `CURRENT_SHAPE` новой формой (дифф PR покажет, что изменилось);
3. дописать строку в `SHAPE_HISTORY` с отпечатком, который напечатал тест (старые строки не переписывать);
4. с этапа 5 — добавить перенос в `MIGRATIONS` (`{ [старая версия]: (мир) => мир новой версии }`) и тест.

До этапа 5 сохранения прошлых версий честно отказываются открываться («сохранение сделано старой версией игры…»).
`loadWorld` проверяет контрольную сумму до переносов, а переносы применяет цепочкой (1 → 2 → 3).

### В браузере

| Модуль | Что делает |
|--------|------------|
| `src/app/saveSlot.ts` | Слот автосохранения в localStorage (`first-campfire/autosave`): чтение, запись, ошибки (переполнение, запрет хранилища) — текстом для игрока |
| `src/app/savedGame.ts` | Какой мир открыть (`openWorld`), автосохранение (`createAutosave`, `saveOnLeave`), «Новый мир» (`startNewWorld`), отладочные заготовки `slot=`, имя файла. Без DOM — тесты в Node |
| `src/app/saveFiles.ts` | Выгрузка сохранения файлом и выбор файла |
| `src/app/titleMenu.ts` | Меню заставки: «Продолжить», «Новый мир» с зерном, «Загрузить из файла»; заметка под названием (почему сохранение не открылось, вопрос перед тем, как стереть мир) |
| `src/app/worldScene.ts` | Сцена `world`: мир из слота, автосохранение, панель «Мир» («Сохранить в файл», «В меню») |

- **Слот — единственный источник «текущей игры».** «Новый мир» и «Загрузить из файла» кладут мир в слот и
  открывают `?scene=world`; сцена читает мир из слота (пустой слот — новый мир со случайным зерном). Поэтому
  перезагрузка страницы возвращает в тот же мир на том же тике.
- **Автосохранение** — когда начинается новый игровой год и когда страница уходит (`pagehide`; `visibilitychange`
  → скрыта — на телефоне это последний надёжный момент). localStorage синхронный, запись успевает. Неудачная
  запись (переполнение — Chromium вмещает ≈ 5,2 млн знаков, ≈ 600 лет нынешнего мира) — сообщение в панели «Мир»,
  повтор только при следующем поводе. Без хранилища (частный режим) — предупреждение в меню, мир не сохраняется.
- **Мир из адреса** (`?scene=world&seed=5&ticks=3000`) — картинка для скриншотов и отчётов: слот не читается и не
  пишется, панель так и говорит. В замороженном кадре (`frame=`) случайных зёрен нет: берётся `seed=`.
- **Испорченное или чужое сохранение** не роняет игру: сцена `world` показывает заставку с причиной и меню,
  «Новый мир» заменяет испорченное без вопроса. Перед тем как стереть **рабочий** мир, меню спрашивает.
- **Отладочный параметр `slot=`** кладёт заготовку в слот до запуска сцены: `world` (мир из `seed=`/`ticks=`, как
  будто в него играли), `broken` (обрезанное сохранение), `alien` (чужой файл), `newer` (из более новой версии),
  `empty` (пусто). Примеры: `?scene=title&slot=world&seed=7&ticks=9000&frame=12` — меню с «Продолжить»;
  `?scene=world&slot=broken&seed=7&ticks=9000` — что видит игрок с испорченным сохранением.
- Сцена `world` рисует мир картой (`src/app/mapView.ts`, шаг 1.1) через камеру наблюдателя (шаг 1.2, раздел
  «Камера»); в панели «Мир» — дата, тик, скорость, масштаб и клавиши. Вид ядра (`createClockView`: небо, светлячки, часы, журнал) остался у отладочной сцены `clock`.

### Заготовка: ежегодные снимки для таймлапса (GDD §11.4) — не реализовано

Таймлапс («ускоренный повтор роста поселения от первого костра до сегодня») и «Тогда и сейчас» нужны и после
загрузки, и для мира, проигранного без графики, поэтому снимки — **часть мира**, а не записи наблюдателя
(в отличие от статистики, ADR-015). Задумано так (сделает шаг 11.6, уточнит его карточка):

- **Поле мира** `world.timelapse`: список снимков `{ year, tick, … }`, по одному на игровой год. Снимок делает
  последняя в `SYSTEMS` система в тик события `year_started` — детерминированно, как всё в мире; он входит в хэш и
  в сохранение, поэтому одно зерно даёт один таймлапс.
- **Что в снимке** — только видимое сверху: вид каждого тайла (грунт, покрытие, объект или здание) одним байтом
  «облика» — `Uint8Array` размером с карту; жители не нужны (таймлапс — про поселение). Масштаб — тайл в пиксель:
  карта 512×512 — 256 КБ на снимок до сжатия.
- **Компактность:** снимок хранится как разница с предыдущим (меняются стройки и вырубки — проценты карты) и
  сжимается повторами (RLE); первый снимок — целиком. Цель — единицы КБ на год, 200 лет — сотни КБ; размер
  сохранения с таймлапсом — показатель в отчёте шага 11.6 (карточка: «размер сохранения остаётся разумным»).
- **Чтение** — в `src/render`: развернуть цепочку разниц в кадры и проиграть; отметки вех берутся из журнала.
- Формат снимка меняет форму мира — подъём `SAVE_VERSION` по общему правилу (с этапа 5 — с переносом: у старых
  миров таймлапс начнётся с года загрузки).

## Игровой цикл

`src/app/loop.ts` — фиксированный шаг симуляции. Реальное время между кадрами переводится в целые тики:
10 тиков в секунду на ×1 (`TIME.ticksPerSecond`). Скорости `SPEEDS`: пауза, ×1, ×2, ×5, ×20.
Число тиков зависит только от прошедшего времени, а не от частоты кадров.

- **Защита от «спирали смерти».** Один кадр засчитывается не больше чем за 250 мс реального времени
  (фоновая вкладка не вызывает лавину тиков), а на расчёт тиков в кадре отводится не больше 30 мс.
  Не уместившиеся тики отбрасываются — мир замедляется, а не вешает страницу; `loop.lagging` сообщает об этом.
- **Интерполяция.** `loop.alpha` (0…1) — насколько реальное время продвинулось к следующему тику. Отрисовка
  показывает состояние между предыдущим и текущим тиком: например, у светлячка есть `prevX` и `x`.
- **Сцена с миром** (`Scene.update`) крутит свой цикл; `src/main.ts` передаёт ей время кадра. В режиме
  `frame=` (замороженный кадр) `update` не вызывается — мир стоит ровно на тике из `ticks=`.
- Клавиши скорости — `src/app/controls.ts`: пробел — пауза, 1–4 — ×1, ×2, ×5, ×20.

## Графика

**Порядок кадра карты** (с шага 1.5, `src/app/mapView.ts`): мир (земля сезона, тени, объекты с сезонной подменой, жители;
с 1.10 замёрзшие вздрагивают на пиксель) в буфер 1:1 → дым костра → дождь или снег (1.10) → свет
времени суток × погода (1.10) на буфер (`shadeRect`: пиксели мира, поэтому кольца света будут резкими на любой ступени) → светлячки
(светятся сами) → знаки (`drawSigns`) → отладка → буфер на экран (`drawPicture`). `light=0` — без света.

Направление зависимостей: `app → render → art`. `src/art` — чистые функции без браузера (тесты в Node), холст —
только в `src/render`; это проверяет `tests/architecture.test.ts`.

**Холст — в физических пикселях** (шаг 1.2): `src/main.ts` даёт сцене размер холста в физических пикселях и
`devicePixelRatio` — `Scene.resize(ширина, высота, ratio)`; сцена выбирает целый масштаб от них. Иначе на экране с
дробным масштабом (Windows 125 %) браузер растягивал бы холст в пиксели разной ширины. Размер — окно × ratio с
округлением; `ResizeObserver` (`device-pixel-content-box`) уточняет его и сообщает о смене ratio. При ratio 1
ничего не меняется.

### Камера

Появилась на шаге 1.2 (ADR-020). Наблюдатель двигает вид мира и приближает его (GDD §1.3, §10.1). Камера — состояние
**отрисовки**: её нет в мире, сохранении и хэше, история от неё не зависит (правило 1).

- **Положение** — точка мира в центре экрана, в пикселях мира (дробная во время движения); **ступень** — `0.5`, `1`,
  `2`, `4` (`ZOOMS`). Ступень в физических пикселях — `pixelScale(ступень, ratio)`: целое число на пиксель мира
  (ratio округляется: 1,25 → ×1, 2 → ×2) или 0,5.
- **Вид** — `cameraLayout(камера, экран, мир)`: масштаб, целое смещение мира на экране, видимая часть мира. Рисуется
  только она: `createMapRenderer(…).draw(ctx, timeMs, layout.view)` в буфер 1:1, затем `drawPicture` кладёт буфер на
  экран. На ×0,5 угол видимой части — чётный пиксель мира, а источник сдвинут на полпикселя: показывается каждый
  второй (нечётный) пиксель, всегда одни и те же — без сглаживания и мерцания. Буфер на пиксель больше видимой части.
- **Края** — `clampCamera`: где карта больше экрана, вид не выходит за край; где меньше — карта по центру.
- **Зум к точке** — `zoomCameraAt` / `cameraHolding`: точка мира под курсором остаётся под ним (до полупикселя), если
  край не мешает.
- **Плавный зум** (ADR-022, отзыв владельца) — `CameraControl` за `ZOOM_MS` (250 мс) ведёт масштаб от прежней ступени к
  новой, держа точку под курсором; кадры перехода — `layoutAt(центр, дробный масштаб, …)`, последний — ровно
  `cameraLayout` ступени (резкий). `camera` — куда придёт камера, `layout` — что нарисовано сейчас, `zooming` — идёт
  ли переход (проверкам — `window.__fc.camera.zooming`).
- **Управление** — `src/app/cameraControl.ts`: `createCameraControl(мир, точка, ступень)` хранит камеру и скорость
  (`update(мс)` — плавное движение, `drag`, `release` — бросок, `zoomBy`, `hold` — клавиши), чистые разборщики ввода
  (`cameraKey`, `createWheelZoom`, `createGestures`) и `bindCameraInput(холст, окно, камера, onTap?)` — события
  страницы. Тесты — в Node, ввод в браузере — сценарии камеры в `npm run e2e`.
- **Щелчок по миру** (шаг 1.3) — касание: одиночный указатель, ушедший от места нажатия не дальше `TAP_SLOP`
  (6 CSS-пикселей), карту не двигает, отпускание даёт команду `tap` с точкой (физические пиксели холста) — её слышит
  `onTap`. Ушёл дальше — перетаскивание, картинка сразу догоняет весь путь от нажатия. Щелчок по жителю выбирает его (шаг 1.6),
  мимо — снимает выбор, а с отладкой `debug=1` — отправляет выбранного на тайл (шаг 1.3).
- **Полёт к точке** (шаг 1.6) — `flyTo(точка)`: за `FLY_MS` (0,8 с) плавно в начале и в конце, на той же ступени,
  край карты останавливает; перетаскивание, бросок, клавиши, зум прерывают (`flying` — летит ли).
- **Адрес** — `zoom=` (ступень; без него — ×2, `DEFAULT_ZOOM`) и
  `cam=x,y` (тайлы; без него — место для стоянки `findCampSite`). Перевод щелчка в тайл:
  `screenToWorld(camera.layout, x, y)` / 16, где x, y — физические пиксели холста.

**Время показа.** `src/main.ts` передаёт сцене номер кадра показа: 10 в секунду (`PRESENTATION_FPS` в
`src/app/scene.ts`). Анимации спрайтов переводят его во время (`frame × 100 мс`) и выбирают кадр по длительностям,
поэтому `?frame=N` всегда даёт одну и ту же картинку. Это время показа, а не время симуляции: анимация не влияет
на мир.

Все строки, которые видит игрок, — по-русски и живут в одном модуле: **`src/ui/texts.ts`** (шаг 1.6, ADR-026), чтобы
на шаге локализации их не пришлось вылавливать по коду.

- **Как пользоваться**: константы и функции по разделам — `MENU`, `HUD`, `SAVE_TEXT`, `DEBUG`, `START`, сцены `CLOCK`,
  `DATA_SCENE`, `GALLERY`, `PALETTE_SCENE`, `STYLESHEET`; события журнала — `describeEvent`, `describeCause`, строки ленты —
  `feedText` (по имени — `FeedWho`, шаг 2.1); жители — `doingOf`, `needsLine`, `villagerName`, `deathNote`; карточка

  `loadWarningText`; числа — `plural(n, FORMS.world)` («5 миров»), `countOf`, `formatCount`, `speedName`, `zoomName`.

## Панель наблюдателя

`src/ui/hud.ts` (шаг 1.6, ADR-026) — интерфейс сцены `world` поверх холста (DOM), по краям экрана: полоса сверху (дата,

**Карточка жителя** (шаг 2.1, ADR-036): портрет (`portrait(житель)` от сцены — свой спрайт и цвета, голова и плечи, ×4),
имя, «мужчина, 22 года», откуда (пришёл при сотворении / родился когда), «Сейчас» (`doingOf`) и «Почему» (`whyOf` — по

(новое сверху, с датой). Семья и память пересобираются, только когда меняются. Умерший выбранный — «Имя †» и «умерла на
N-й день — голод». Открыть карточку адресом — `select=N`. На компьютере карточка не выше `100% − 280px` (под лентой из
пяти строк; длинное — прокруткой), на телефоне — до 46 % высоты. Панель только читает мир; меняет

### Проверка кадров

Появилась на шаге 0.8 (ADR-017). `npm run shot` не только снимает кадр, но и умеет проверить его по пикселям:

```
npm run shot -- --out out/crisp --check-crisp 4 x4="?scene=stylesheet&zoom=4&frame=5&ui=0"
npm run shot -- --out out/control --compare docs/screenshots/0.7 world-loaded="?scene=world&slot=world&seed=7&ticks=9000&frame=0"
```

- **`--check-crisp N`** — снимок резкий на ×N: при лучшем сдвиге сетки (картинка стоит по центру) каждый квадрат
  N×N одноцветный. Размытие (сглаживание, дробный масштаб или положение) смешивает соседей — кадр падает с числом
  смешанных квадратов и местом первого. Только с `ui=0`: текст и HTML — не пиксель-арт. N — в пикселях снимка
  (при `--scale 2` картинка ×2 — это ×4).
- **`--compare папка`** — каждый кадр сравнивается с кадром того же имени в папке (номер `NN-` не важен):
  «пиксель в пиксель» или сколько пикселей отличается и в каком прямоугольнике. Отличия не роняют команду —
  это повод посмотреть глазами (например, в шапке галереи меняется время сборки атласа).
- **`--frame-time мс`** (шаг 1.1) — живая страница (без `frame=` в адресе) работает столько миллисекунд, затем
  печатается, сколько рисуется кадр: среднее, 99 % кадров, худший и отдельно первый (он платит за подготовку —
  холсты уходят в видеопамять). Источник — `window.__fc.renderMs` (`src/main.ts`). Пример:
  `npm run shot -- --out out/perf --frame-time 4000 fit@1088x1088="?scene=world&seed=7&ui=0"`. В облачной сессии
  Chromium рисует без видеокарты — на настоящем компьютере быстрее.
- **`--check-half папка`** (шаг 1.2) — кадр на ×0,5 — это кадр того же места на ×1 «через пиксель»: каждый его
  пиксель равен пикселю кадра того же имени в папке, снятого на ×1 (тот же `cam=`, окно вдвое больше, тот же
  `--scale`). Сглаживание смешивает соседей — кадр падает. Пример:
  `npm run shot -- --out out/half-ref m@2560x1440="?scene=world&seed=1&frame=5&ui=0&zoom=1"`, затем
  `npm run shot -- --out out/half --check-half out/half-ref m="?scene=world&seed=1&frame=5&ui=0&zoom=0.5"`.
- PNG читает `tools/png.ts` (8 бит, RGB/RGBA, без чересстрочности — так пишет Chromium), проверки — чистые функции
  `tools/imageChecks.ts` (тесты рядом).
