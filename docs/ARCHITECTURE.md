# Архитектура

Документ описывает, как устроен код и какие правила нельзя нарушать. Он должен соответствовать реальному коду:
изменил устройство — обнови документ в том же PR. Обоснования решений — в [`DECISIONS.md`](DECISIONS.md).

## Технологии

| Что                     | Чем                                                       | Примечание                                                              |
| ----------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| Язык                    | TypeScript (строгий режим)                                | Только «стираемый» синтаксис: Node запускает `.ts` напрямую, без сборки |
| Сборка и dev-сервер     | Vite                                                      | `npm run dev`, `npm run build` → `dist/`                                |
| Отрисовка               | Canvas 2D, собственный лёгкий рендерер                    | Без движка; см. ADR-002                                                 |
| Интерфейс               | HTML/CSS поверх холста                                    | `#ui` в `index.html`                                                    |
| Звук                    | Web Audio, процедурный синтез                             | Появится на этапе 5                                                     |
| Тесты                   | Vitest                                                    | `*.test.ts` рядом с кодом, сценарные — в `tests/`                       |
| Линтер и форматирование | Biome                                                     | `npm run lint`, `npm run format`                                        |
| Скриншоты               | Playwright + Chromium (предустановлены в облачной сессии) | `tools/screenshot.ts`; в `package.json` не добавлять                    |
| CI                      | GitHub Actions                                            | `.github/workflows/ci.yml` — те же проверки, что `npm run check`        |
| Публикация              | GitHub Pages                                              | `.github/workflows/deploy.yml`, после слияния в `main`                  |

Библиотек времени выполнения нет, и по умолчанию они не добавляются. Нужна зависимость — запись в `DECISIONS.md`.

## Структура каталогов

```
data/            таблицы содержания и баланса (*.json): ресурсы, здания, технологии, черты, сценки…
src/
  sim/           СИМУЛЯЦИЯ: состояние мира и системы. Чистая, детерминированная, без браузера
  data/          типы таблиц, их загрузка и проверка
  art/           графика как код: палитра, описания спрайтов, растеризатор, атлас
  render/        отрисовка мира на Canvas 2D: камера, тайлы, спрайты, свет, частицы
  ui/            интерфейс наблюдателя (HTML/CSS): панель, карточки, летопись, слои
  app/           запуск: параметры адресной строки, сцены, игровой цикл, ввод
  main.ts        точка входа
tools/           скрипты Node: дорожная карта, скриншоты, прогоны без графики
tests/           сквозные тесты: архитектурные правила, детерминизм, сценарии
docs/            вся документация проекта (см. docs/PROCESS.md, «Где что лежит»)
```

Направление зависимостей — строго в одну сторону:

```
app → ui, render → art
app, ui, render → sim → data
```

`sim` и `data` не импортируют ничего из `render`, `ui`, `app`, `art`. Это проверяет `tests/architecture.test.ts`.

## Правила, которые нельзя нарушать

### 1. Детерминизм: одно зерно — одна история

- Вся случайность — только через генератор случайных чисел симуляции, состояние которого хранится в мире.
  `Math.random`, `Date`, `performance.now`, таймеры в `src/sim` запрещены (проверяется тестом).
- Время симуляции — это номер тика. Скорость игры меняет число тиков в секунду, но не результат.
- Порядок обхода сущностей фиксирован (массивы, сортировка по id). Результат не должен зависеть от порядка
  вставки в `Map`/`Set`, от кадровой частоты, от размера окна, от положения камеры.
- У каждой системы свой именованный поток случайных чисел, чтобы новая система не сдвигала историю остальных
  сильнее необходимого.
- Тест детерминизма сравнивает хэш состояния двух прогонов одного зерна. Если он упал — ищи источник
  недетерминизма; править сам тест нельзя.
- Уровни детализации (GDD §2.4) не должны менять историю в зависимости от того, куда смотрит камера:
  упрощение определяется правилами симуляции, а не экраном. Решение об этом принимается на шаге 6.11.

### 2. Симуляция отдельно от отрисовки

- `src/sim` ничего не знает об экране. Та же симуляция работает в Node без графики (`npm run sim`) —
  это главный инструмент баланса.
- Отрисовка и интерфейс только **читают** состояние. Никакая игровая логика не живёт в `render`/`ui`.
- Плавность движения — интерполяция в отрисовке между двумя тиками, а не дробные тики в симуляции.
- Симуляция сообщает о происходящем через **журнал событий** (рождение, смерть, открытие, начало стройки…).
  Из него питаются летопись, звук, пузырьки, сценки, статистика.

### 3. Содержание — в таблицах данных

- Ресурсы, здания, технологии, черты, профессии, сценки, числа баланса — в `data/*.json`.
  В коде — механики, а не списки содержания. Критерий: новый ресурс или новое здание существующего типа
  добавляется строкой в таблице, без правки кода.
- Таблицы проверяются при загрузке и тестами: типы полей, обязательные поля, ссылки между таблицами.
  Ошибка в таблице должна называть файл, запись и поле.
- Идентификаторы в данных — `snake_case` латиницей (`berry_bush`). Названия для игрока — по-русски, отдельным полем.

### 4. Причинность

- У каждого события, решения, постройки, закона хранится **причина** (ссылка на событие или нужду, которые к нему привели).
  Наблюдатель всегда должен иметь возможность получить ответ на вопрос «почему?» (GDD, столп 1).
- Ничего не происходит «по таймеру сценария». Режиссёр событий только сдвигает вероятности.
- Каждый житель ведёт короткий журнал решений (что выбрал и почему) — он нужен для отладки и для поиска
  «нелепых смертей» в прогонах.

### 5. Физичность

- Ресурсы — физические предметы: лежат на тайле, в куче, в хранилище или в руках. Ничего не телепортируется
  и не возникает из воздуха; количество предметов сохраняется (это проверяется тестами-инвариантами).
- Труд виден: у каждого действия есть место, длительность и анимация.

### 6. Каждая технология видна на экране

Технология без видимого проявления (предмет, здание, анимация, деталь одежды, изменение ландшафта) не принимается (GDD §7.5).

### 7. Состояние мира — простые данные

- Мир — обычные объекты, массивы и типизированные массивы, которые целиком сериализуются (сохранение, хэш, снимки
  для таймлапса). Без классов с поведением внутри состояния, без замыканий, без ссылок на DOM.
- Ссылки между сущностями — по числовым id, а не по указателям.
- У сохранения есть номер версии формата. С этапа 5 старые сохранения обязаны открываться (миграции).

### 8. Воспроизводимость экрана

- Любое состояние игры достижимо адресной строкой: `?scene=…&seed=…&ticks=…&cam=x,y&zoom=…&ui=0`.
  Это основа скриншотов и отчётов об ошибках. Новая сцена или режим — значит, новый параметр.
- Сцены регистрируются в `src/app/scenes.ts`. Отладочные сцены (галерея спрайтов, палитра, песочницы) — тоже сцены.
- Страница сообщает о готовности через `window.__fc.ready` и об ошибках через `window.__fc.errors` —
  на это опирается `tools/screenshot.ts`.

### 9. Производительность — с первого дня

Целевые бюджеты (уточняются ревизиями этапов):

| Показатель                              | Цель                          |
| --------------------------------------- | ----------------------------- |
| Тик симуляции при 100 жителях           | ≤ 1 мс                        |
| Тик симуляции при 1500 жителях          | ≤ 8 мс (иначе ×20 невозможна) |
| Кадр отрисовки                          | ≤ 16 мс на среднем компьютере |
| Прогон без графики: 100 лет, 40 жителей | ≤ 30 с на зерно               |

Меряй, а не угадывай. Замеры — в отчёте шага и в `STATUS.md`.

## Графика

- Проекция ¾ сверху, тайл 16×16, взрослый житель 12×18, целочисленный масштаб, сглаживание выключено (GDD §10.1).
- **Графика — это код**: спрайт описывается текстовой сеткой символов и палитрой в `src/art/`; растеризуется
  в атлас при запуске. Файлов-картинок в репозитории нет (кроме скриншотов). Перекраска (тон кожи, сезон, эпоха) —
  подмена палитры. Подробности появятся в `docs/ART.md` на шаге 0.3.
- Все цвета — из мастер-палитры. Цвет «мимо палитры» — ошибка, которую ловит тест.

## Тексты

Все строки, которые видит игрок, — по-русски и проходят через единый модуль текстов (появится вместе с HUD),
чтобы на шаге локализации их не пришлось вылавливать по коду.

## Тестирование

| Вид            | Где                          | Что проверяет                                                                |
| -------------- | ---------------------------- | ---------------------------------------------------------------------------- |
| Модульные      | `src/**/*.test.ts`           | Отдельные функции и системы                                                  |
| Архитектурные  | `tests/architecture.test.ts` | Чистота `src/sim` и `src/data`                                               |
| Детерминизм    | `tests/` (с шага 0.2)        | Одинаковый хэш мира для одного зерна; сохранение/загрузка не меняют историю  |
| Сценарные      | `tests/`                     | Маленький мир + условие: «двое не умирают неделю», «голодный бросает работу» |
| Инварианты     | `tests/`                     | Сохранение количества предметов, отсутствие жителей в воде и т. п.           |
| Статистические | `npm run sim`                | Сотни миров без графики: выживаемость, темп, причины смертей (GDD §15.2)     |
| Визуальные     | `npm run shot`               | Страница без ошибок + просмотр кадров глазами                                |

Сценарный тест — основной способ закрепить критерий готовности шага: он остаётся в наборе навсегда и не даёт
будущим шагам сломать поведение.
